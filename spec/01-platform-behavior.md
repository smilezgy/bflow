# Bflow —— 渠道行为规格（P0 探测产出）

> **本文档是 Bflow clean-room 重写的唯一知识来源。**
>
> 采集方式：黑盒 HTTP 实测（`tools/probe_platforms.py`），记录可观察事实
> —— HTTP 状态码、响应报文原文、产物真实格式/尺寸、是否计费。
> 采集过程中**未复制**被测项目的任何源码；本文档只描述**行为**，不含代码表达。

## 读法约定

| 标记 | 含义 |
|---|---|
| ✅ | 该渠道支持，且行为符合请求 |
| ⚠️ | 支持但行为与请求不符（产物格式/尺寸被改写） |
| ❌ | 明确拒绝，返回错误报文 |
| — | 未探测 |

**计费推断规则**：HTTP 200 视为已生成并计费；非 200 视为未生成、未计费。

### 渠道代号说明

本文档**只用代号**指代被测渠道，不出现真实渠道名称与域名。

原因有二：

1. 本仓库公开，列出第三方商业渠道的名称与域名等同于替其做推广；
2. 规格的价值在于**行为差异**，与「哪家渠道」无关 —— 代号足以支撑实现。

| 代号 | 行为特征（这是识别它的唯一依据）|
|---|---|
| **CH-A** | 行为最规范，唯一完整 honor `output_format` 的渠道，尺寸越界时静默归一化 |
| **CH-B** | 严格模式：尺寸越界即报错，部分格式被静默丢弃，英文报错 |
| **CH-C** | 输出格式与请求完全无对应关系，尺寸走固定输出值，**中文报错** |
| **CH-D** | 能力随 key 分组变化，同一渠道在不同分组下支持不同格式 |
| **CH-E** | 上游暂时不可用（503）|
| **CH-F** | 新版模型无通道，仅旧版模型可用 |

实际渠道信息保存在**本地配置** `channels.json`（已 gitignore），
仓库内仅提供脱敏模板 `channels.example.json`。

## 0. 渠道总览

| 渠道 ID | 名称 | Base URL | gpt-image-2.6-flare | 备注 |
|---|---|---|---|---|
| `ch-b` | CH-B | `https://<base-url>` | ✅ 200 | |
| `ch-a` | CH-A | `https://<base-url>` | ✅ 200 | 行为最规范，作为参考基线 |
| `ch-e` | CH-E | `<base-url>/v1` | ❌ 503 | `Image generation is temporarily unavailable` |
| `ch-c` | CH-C | `<base-url>` | ✅ 200 | **输出格式完全错乱，见 §3**；报错为中文 |
| `ch-f` | CH-F | `https://<base-url>` | ❌ 503 | 分组 <group>无 gpt-image-2.6 通道；`gpt-image-2` ✅ 200 |
| `ch-d` | CH-D | `https://<base-url>` | ⚠️ 503 | 分组 <group> 下无 gpt-image-2.6 通道（分组能力会变）|

> **URL 拼接**：base 已含 `/v1` 时直接追加端点，否则补 `/v1/<endpoint>`。
> ch-e 的 base 含 `/v1`（`api.CH-E.club/v1`）。

### 通用错误报文样本

| 场景 | HTTP | 报文原文 |
|---|---|---|
| 模型无通道（中转聚合平台） | 503 | `{"error":{"code":"model_not_found","message":"分组 <group> 下模型 gpt-image-2.6-flare 无可用渠道（distributor） (request id: ...)"}}` |
| 上游暂时不可用 | 503 | `{"error":{"message":"Image generation is temporarily unavailable","type":"upstream_error"}}` |
| 路径错误 | 404 | `{"error":{"message":"Invalid URL (POST /v1/v1/images/generations)","type":"invalid_request_error","param":"","code":""}}` |
| SVG 内容不适合 | 503 | `{"error":{"message":"SVG output could not be generated for this prompt. SVG works best for icons, logos and flat illustrations. ...","type":"shell_api_error","param":"","code":"svg_generation_failed"}}` |
| SVG 分组不支持 | 400 | `{"error":{"message":"SVG output is not available in this key's group (per-call route). Create a key with OpenAI Official as its group ...","type":"shell_api_error","param":"","code":"invalid_request"}}` |
| SVG 分组不支持（简化措辞） | 400 | `{"error":{"message":"SVG output is not available in this key's group (per-call route)."}}` |

> **关键观察**：所有 `gpt-image-2.6` 相关错误报文里**都不含 `output_format` 这个参数名**，
> 只出现格式值（`SVG`）或错误码（`svg_generation_failed`）。
> → 规格结论：**不能靠「报文点名参数」来判断格式能力**，必须靠黑盒能力表。

## 1. CH-B（ch-b）—— 严格模式

模型：`gpt-image-2.6-flare`　端点：`POST {base}/v1/images/generations`

### 1.1 输出格式

| 请求 output_format | HTTP | 实际格式 | 实际尺寸 | 结论 |
|---|---|---|---|---|
| `png` | 200 | png | 1024×1024 | ✅ |
| `jpeg` | 200 | jpeg | 1024×1024 | ✅ |
| `webp` | 200 | **png** | 1024×1024 | ⚠️ **静默丢弃 webp** |
| `svg` | 200 | **png** | 1024×1024 | ⚠️ **静默丢弃 svg** |
| `gif` | 400 | — | — | ❌ 见 §1.3 |

> **规格结论**：`output_format` 中 `webp` / `svg` 被**静默丢弃**（不报错），
> 产物按 PNG 处理。调用方无法从状态码察觉 → 必须靠魔数核对。

### 1.2 尺寸边界（严格报错，不静默改写）

| 请求尺寸 | HTTP | 报文要点 | 实际尺寸 |
|---|---|---|---|
| 256×256 | 400 | `Requested resolution is below the current minimum pixel budget.` | — |
| 512×512 | 400 | 同上 | — |
| 768×768 | 400 | 同上 | — |
| 896×896 | 200 | | 896×896 |
| 1024×1024 | 200 | | 1024×1024 |
| 1536×1024 | 200 | | 1536×1024 |
| 2048×2048 | 200 | | 2048×2048 |
| 3072×3072 | 400 | `Requested resolution exceeds the current pixel budget.` | — |

→ 下限落在 768（失败）与 896（成功）之间，总像素约 **655,360**（≈816×816）。
→ 上限：2048²（419 万）通过，3072²（943 万）失败，约 **829 万**像素。
→ 长边上限 3840（见 GIF 报文）。

### 1.3 GIF 限制

请求 `output_format=gif` + `frame_count=4` + `frame_duration_ms=200` @1024×1024：

```
400 {"error":{"message":"No supported sheet fits 4 GIF frames at size '1024x1024'.
Invalid size '4096x2048'. The longest edge must be less than or equal to 3840.
Invalid size '2048x4096'. The longest edge must be less than or equal to 3840. ..."}}
```

→ 平台把所有帧拼成一张 sheet 再编码。请求 4 帧时平台尝试的拼版是 **4096×2048**
（4 帧 = 2×2 排列，每帧 2048×1024，即每帧被放大到 2 倍）。
→ 报文里出现的长边/像素预算，是**平台自己尝试的拼版尺寸**，不是用户请求的尺寸。

### 1.4 质量与复杂度：全部支持

| 参数 | 取值 | HTTP |
|---|---|---|
| quality | auto / low / medium / high / **xhigh** / **max** | 全部 200 ✅ |
| complexity | low / medium / high | 全部 200 ✅ |
| background | auto / transparent / opaque | 全部 200 ✅ |
| n | 1、2 | 全部 200 ✅ |
| 未知参数 | `zzz_bogus_param` | 200 ⚠️ 静默忽略 |

### 1.5 压缩率：**webp 被丢弃的铁证**

| 组合 | HTTP | 实际格式 | 结论 |
|---|---|---|---|
| png + comp=80 | **400** | — | `Compression less than 100 is not supported for PNG output format` |
| png + comp=100 | 200 | png | ✅ |
| jpeg + comp=80 | 200 | jpeg | ✅ |
| jpeg + comp=100 | 200 | jpeg | ✅ |
| **webp + comp=80** | **400** | — | **报的是 PNG 的压缩冲突** |
| **webp + comp=100** | 200 | **png** | **铁证：webp 被静默丢弃** |

> **关键推理**：`webp + comp=80` 的报错内容是「PNG 不接受 <100 压缩率」——
> 说明请求虽然写了 webp，**平台实际按 PNG 处理**。再用 `webp + comp=100`
> （PNG 能接受 100）成功且产物为 png，双重确认 webp 被丢弃。

→ 规格结论：**压缩冲突报错可以用来间接探测渠道的真实格式处理**，
这是本次探测方法的一个可复用技巧。

## 2. CH-A（ch-a）—— 参考基线

模型：`gpt-image-2.6-flare`　端点：`POST {base}/v1/images/generations`

### 2.1 输出格式

| 请求 output_format | HTTP | 实际格式 | 实际尺寸 | 结论 |
|---|---|---|---|---|
| `png` | 200 | png | 1024×1024 | ✅ |
| `jpeg` | 200 | jpeg | 1024×1024 | ✅ |
| `webp` | 200 | webp | 1024×1024 | ✅ |
| `svg` | 200 | svg | —（矢量无像素尺寸） | ✅ |
| `gif` | 200 | gif | **960×960** | ⚠️ 平台自行缩小 |

> **GIF 帧数**：请求 `frame_count=4` / `frame_duration_ms=200`，平台返回 960×960，
> 说明平台**自行决定**帧数与画布缩放，客户端传入的帧参数不生效。

### 2.2 尺寸：**静默归一化**（与 CH-B 相反）

| 请求尺寸 | HTTP | **实际尺寸** | 结论 |
|---|---|---|---|
| 256×256 | 200 | **1024×1024** | ⚠️ 静默放大 |
| 512×512 | 200 | **1024×1024** | ⚠️ 静默放大 |
| 768×768 | 200 | **816×816** | ⚠️ 静默归一化到下限 |
| 896×896 | 200 | 896×896 | ✅ |
| 1024×1024 | 200 | 1024×1024 | ✅ |
| 1536×1024 | 200 | 1536×1024 | ✅ |
| 2048×2048 | 200 | 2048×2048 | ✅ |
| 3072×3072 | 200 | **2880×2880** | ⚠️ 静默缩小到上限内 |

→ **规格结论**：同一模型、不同渠道对尺寸的处理**完全相反**：
CH-B 越界就报错，CH-A 越界就静默改写。
→ **调用方必须以产物真实尺寸为准**，并在使用前告知用户实际尺寸。

### 2.3 质量档：全部支持

| quality | HTTP | 结论 |
|---|---|---|
| `low` / `medium` / `high` / `xhigh` / `max` / `auto` | 200 | ✅ 全部接受 |

→ `gpt-image-2.6` 系列提供 `xhigh` / `max` 两档高于 `high` 的质量。

### 2.4 complexity：全部支持

| complexity | HTTP | 结论 |
|---|---|---|
| `low` / `medium` / `high` | 200 | ✅ 全部接受 |

→ `complexity` 控制出图前的规划力度，与 `quality` 独立（渲染质量）。

### 2.5 background：全部接受

| background | HTTP | 实际格式 | 结论 |
|---|---|---|---|
| `auto` | 200 | png | ✅ |
| `transparent` | 200 | png | ⚠️ 需另测透明度（本次未校验 alpha 通道）|
| `opaque` | 200 | png | ✅ |

→ 规格要求：`transparent` 时产物格式必须允许 alpha（png / webp），
jpeg 不支持透明背景。

### 2.6 压缩率 × 格式：全部兼容

| 组合 | HTTP | 实际格式 | 结论 |
|---|---|---|---|
| png + comp=80 / 100 | 200 | png | ✅ PNG 忽略压缩率 |
| jpeg + comp=80 / 100 | 200 | jpeg | ✅ |
| webp + comp=80 / 100 | 200 | webp | ✅ |

→ 与 CH-B 系不同，CH-A **不会**因「PNG 不接受 <100 压缩率」而报错。
→ 规格要求：压缩率按格式分别处理（png 不传压缩率、jpeg/webp 传）。

### 2.7 数量与未知参数

| 用例 | HTTP | 结论 |
|---|---|---|
| `n=1` | 200 | ✅ |
| `n=2` | 200 | ✅ |
| 未知参数 `zzz_bogus_param` | 200 | ⚠️ **静默忽略未知字段**（不报错）|

→ 规格要求：客户端**不能**靠「传个乱字段看报不报错」来探测能力；
必须用黑盒能力表。

### 2.8 平台尺寸归一化规律（推断）

| 请求 | 实际 | 推断规则 |
|---|---|---|
| 256/512 | 1024×1024 | 小于下限时归一化到 1024 |
| 768 | 816×816 | 归一化到最近的下限档（816 = 655,360 开方取 16 倍数）|
| 3072 | 2880×2880 | 归一化到长边上限内（829 万像素 ≈ 2880²）|

> 标注：**推断**，仅 2 个采样点支撑，需要更多采样验证。

## 3. CH-C（ch-c）—— 输出格式完全错乱

模型：`gpt-image-2.6-flare`

### 3.1 实测结果

| 请求 output_format | HTTP | **实际格式** | **实际尺寸** | 结论 |
|---|---|---|---|---|
| `png` | 200 | **webp** | **1254×1254** | ⚠️ 格式错乱 |
| `jpeg` | 200 | **png** | **1254×1254** | ⚠️ 格式错乱 |
| `webp` | 200 | **png** | **1254×1254** | ⚠️ 格式错乱 |
| `svg` | 200 | **png** | **1254×1254** | ⚠️ 格式错乱 |
| `gif` | 200 | gif | **621×623** | ⚠️ 尺寸被改 |

### 3.2 尺寸行为：**固定输出尺寸**

CH-C 对尺寸的处理是「要么精确匹配，要么给固定值」：

| 请求尺寸 | HTTP | 实际尺寸 | 说明 |
|---|---|---|---|
| 256×256 | 200 | **1254×1254** | 固定值 |
| 512×512 | 200 | **1254×1254** | 固定值 |
| 768×768 | 200 | **1254×1254** | 固定值 |
| 896×896 | 200 | **1254×1254** | 固定值 |
| 1024×1024 | 200 | **1254×1254** | 固定值 |
| 1536×1024 | 200 | 1536×1024 | 精确匹配 |
| 2048×2048 | 500 | — | `服务内部错误`（渠道自身缺陷）|
| 3072×3072 | 400 | — | 超出像素上限 |

→ 规格结论：**只有与渠道预设画布匹配的比例才精确输出**，方形请求一律给 1254×1254。
→ 1254×1254 = 1,572,516 像素，落在 655,360 ～ 8,294,400 区间内。

### 3.3 尺寸边界：报错最规范，含明确像素范围

CH-C 的尺寸报错**直接给出可用区间**（中文），这是所有渠道里最有价值的规格信号：

```
400 {"error":{"message":"gpt-image-2.6-flare模型不支持3072x3072尺寸；
     总像素必须在 655360 到 8294400 之间",
     "type":"invalid_request_error","code":"invalid_request"}}
```

→ **总像素下限 655,360（≈816×816），上限 8,294,400（≈2880×2880）**
—— 与 CH-B/严格模式渠道实测的边界完全一致，说明这是 OpenAI 侧的模型约束，
而非渠道自定规则。

### 3.4 质量与复杂度：全部接受

| 参数 | 取值 | 结果 |
|---|---|---|
| quality | low / medium / high / xhigh / max / auto | 全部 200 ✅ |
| complexity | low / medium / high | 全部 200 ✅ |

### 3.5 规格结论（重要）

1. **请求 png 实际得到 webp** —— 该渠道的 `output_format` 与产物**无稳定对应关系**，
   不能假定「请求什么就得到什么」。
2. **尺寸也不受控**：请求 1024×1024，实际 1254×1254（放大了 22%）；
   请求 256×256 同样返回 1254×1254。
3. 该渠道**不报任何错**（全部 200），所以调用方**无法从状态码察觉格式不符**。
   → 规格要求：**必须按产物魔数核对真实格式**，与请求不符时如实告知用户。

> 这条正是 Bflow 中「格式不符提示」功能的必要性依据。

### 3.6 新发现的错误类型

| 场景 | HTTP | 报文 |
|---|---|---|
| 渠道内部故障 | 500 | `{"error":{"message":"服务内部错误，请稍后重试","type":"invalid_request_error","code":"internal_server_error"}}` |

→ 500 属**可重试**错误（未生成、未计费）；规格要求区分「可重试 5xx」与
「参数类 4xx」。

## 4. edits 链路（P1 实测，CH-A）

端点：`POST {base}/v1/images/edits`，`multipart/form-data`

### 4.1 基本可用性

| 用例 | HTTP | 实际格式 | 实际尺寸 | 结论 |
|---|---|---|---|---|
| 单参考图 + prompt | 200 | png | 1024×1024 | ✅ 编辑链路可用 |

### 4.2 参考图数量

| 参考图数 | HTTP | 结论 |
|---|---|---|
| 1 张 | 200 | ✅ |
| 2 张 | 200 | ✅ |
| 3 张 | 200 | ✅ |
| 4 张 | 未完成（超时截断）| 至少支持 3 张 |

→ 多参考图可用（同名字段多次提交）。**上限待补测**。

### 4.3 编辑链路上的可选参数

| 参数 | HTTP | 实际格式 | 结论 |
|---|---|---|---|
| `input_fidelity=high` | 200 | png | ✅ 接受 |
| `input_fidelity=low` | 200 | png | ✅ 接受 |
| `complexity=low` | 200 | png | ✅ 接受 |
| `complexity=high` | 200 | png | ✅ 接受 |
| `output_format=png` | 200 | png | ✅ |
| `output_format=webp` | 200 | png（产物下载超时未取到）| ⚠️ 疑似未 honor，需复测 |

> `input_fidelity` 在 gpt-image-2.6 上**不报错**（与「官方已移除该参数」的认知不同）。
> 说明渠道侧仍在透传/忽略该字段，**不能靠"报错"判断支持度**，要靠能力表。

### 4.4 数量与 mask

| 用例 | HTTP | 结论 |
|---|---|---|
| `n=2` | 200 | ✅ 编辑链路支持多张输出 |
| `mask` 传入非法 PNG 内容 | **200** | ⚠️ **未校验 mask 内容**，静默忽略并正常出图 |

> **mask 校验缺失是重要发现**：上游不校验遮罩文件是否合法，
> Bflow 若要提供「局部编辑」，必须**在客户端侧预校验** mask（尺寸与主图一致、
> 格式合法、含 alpha 通道），否则用户会得到「遮罩没生效」的结果却毫无察觉。

### 4.5 规格要求（edits 链路）

| 编号 | 需求 |
|---|---|
| E-1 | 编辑请求用 multipart，参考图以**同名字段多次提交**（`image`）|
| E-2 | 参考图数量上限需按渠道配置（实测至少 3 张）|
| E-3 | **客户端必须预校验 mask**：尺寸与主图一致、合法 PNG、含 alpha |
| E-4 | `input_fidelity` 等参数在 2.6 上不报错，支持度只能靠能力表判定 |
| E-5 | 编辑链路的 `output_format` 同样可能不被 honor，需按魔数核对 |

## 5. CH-D（ch-d）—— key 分组决定能力

| 请求 | 结果 |
|---|---|
| `output_format=svg`（写实提示词） | 400 `SVG output is not available in this key's group ...` |
| `output_format=svg`（扁平图标提示词） | 503 `svg_generation_failed`（提示词风格限制，非格式限制） |

→ **同一渠道内，key 分组不同 → 格式能力不同**。规格要求：能力表按
`(渠道, 模型, key 分组)` 维度，而非仅按渠道。

## 6. 规格需求清单

以下是从实测中提炼的、**新实现必须满足的行为**：

### 6.1 格式保真与告知

| 编号 | 需求 |
|---|---|
| F-1 | 请求体必须携带用户所选的 `output_format`（不静默改写） |
| F-2 | 产物格式以**魔数**判定，不信任上游声明的 mime 或扩展名 |
| F-3 | 实际格式 ≠ 请求格式时：**交付产物**（上游已计费）+ 明确提示用户 |
| F-4 | 上游明确拒绝该格式（400）时：直接报错，不重试、不换格式 |
| F-5 | 上游 200 但返回别的格式：**不得**当作成功且无提示 |

### 6.2 尺寸

| 编号 | 需求 |
|---|---|
| S-1 | 实际尺寸同样以产物为准，不能假设等于请求尺寸 |
| S-2 | 尺寸下限/上限**因渠道而异**：CH-B 越界报错，CH-A 越界静默改写 → 能力表按渠道存 |
| S-3 | 已知下限 ≈ 655,360 像素（≈816×816），上限 ≈ 829 万像素 / 长边 3840（严格模式渠道实测）|
| S-4 | GIF 单帧长边受拼版预算限制（严格模式渠道实测单帧 < 1024）|

### 6.3 错误分类

| 编号 | 需求 |
|---|---|
| E-1 | 错误分类**不能只靠报文点名参数** —— gpt-image-2.6 系报文常不含参数名 |
| E-2 | 需识别错误码：`svg_generation_failed`（内容限制）/ `invalid_request`（分组限制）/ `model_not_found`（无通道）/ `upstream_error`（暂时不可用）|
| E-3 | 「内容限制」类错误应给出可执行建议（换提示词风格 / 换格式 / 换分组）|
| E-4 | 尺寸类错误需区分「低于下限」与「超上限」两种方向（措辞不同：`below the current minimum` vs `exceeds the current pixel budget`）|

### 6.4 编辑链路

| 编号 | 需求 |
|---|---|
| X-1 | 编辑请求用 multipart，参考图以**同名字段多次提交**（`image`）|
| X-2 | 参考图数量上限按渠道配置（实测至少 3 张）|
| X-3 | **客户端必须预校验 mask**（尺寸与主图一致 / 合法 PNG / 含 alpha）—— 上游不校验，非法 mask 会被静默忽略 |
| X-4 | 参数支持度只能靠能力表判定，不能靠「传了报不报错」（`input_fidelity` 在 2.6 上不报错）|
| X-5 | 编辑链路的 `output_format` 同样可能不被 honor，需按魔数核对 |
